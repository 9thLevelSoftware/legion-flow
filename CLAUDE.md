# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Legion Flow is a CLI-driven autonomous workflow engine (`legion-flow` bin) with human-authority gates. It is the third sibling of `legion-cli` and `legion-ascended` and must never be mistaken for either: the bin is `legion-flow` with no `legion` alias, and the state root is `.legion-flow/`, never `.legion/` or `.legion-cli/`.

## Commands

Toolchain: pnpm 9.15.9 (pinned via `packageManager`), Node >= 22.13.0. Tests have been verified on Node 24.

```bash
pnpm install                 # if pnpm prompts to purge modules in a non-interactive shell, add --config.confirmModulesPurge=false
pnpm run validate:m0         # full gate: build -> typecheck -> test -> check:skills
pnpm run check:skills        # skills tree conformance and generated-manifest drift (node scripts/check-skills.mjs)
node scripts/gen-skill-manifests.mjs   # regenerate .claude-plugin/*, gemini-extension.json, skills/AGENTS.md after editing a SKILL.md
pnpm run build               # tsc in every package (pnpm -r)
pnpm run typecheck           # tsc --noEmit in every package
pnpm run test                # --no-bail: a failure in schema does not stop persist/cli
```

Per-package and single-test:

```bash
pnpm --filter @9thlevelsoftware/legion-flow-persist test
node --test --test-name-pattern "rebaseline" packages/persist/test/persist.test.ts
```

**Build before running any test file directly.** Every package `test` script runs `pnpm run build` first because tests import compiled output: CLI tests import `../dist/index.js`, `bin.test.ts` spawns `dist/bin.js`, and cross-package imports resolve through workspace links to each package's `dist/`. Running `node --test` without a prior build loads stale or missing output.

**Command-surface parity is a test, not a script.** `packages/cli/test/catalog.test.ts` fails the gate if any catalog verb is unregistered, any planned verb does not answer `--json` with a refused envelope, or `help-all` omits a verb.

## Architecture

Fourteen ESM TypeScript packages with a strict dependency direction: `schema` -> `persist` -> {`engine`, `evidence`, `memory`} -> `gates` and {`adapters`, `sandbox`} -> `cli`, plus `egress` (depends on `schema` only; `sandbox` depends on it), `evals` (depends on `schema` only; `cli` composes it into the engine's `evalWorkflow` as a scorer port), `map` (depends on `schema` and `typescript` only), `lsp` (depends on `schema` only; `cli` composes it), and `browser` (depends on `schema`, `engine`, and `playwright-core`; `gates` imports it). `memory` depends on `persist` and `map`; `gates` depends on `memory` for the `architecture_conformance` gate; `adapters` and `sandbox` import `engine` for its ports. A test in `packages/map/test/rules.test.ts` holds this repository to exactly this direction, with no import cycles and none of the excluded frameworks. `engine` depends on `@opentelemetry/api` only (a no-op without a provider); `evidence` owns the provider, processor, and exporter. `engine` declares the ports (`Materializer`, `Adapter`, `CheckRunner`) and imports neither `gates`, `adapters`, nor `sandbox`; `cli` composes them in `execute`. No cross-package relative imports; packages import each other by scoped name (`@9thlevelsoftware/legion-flow-*`) through `workspace:*` links.

- `packages/schema` holds every Zod 4 contract. All schemas are `.strict()`. Document identifiers live in `versions.ts` as `legion-flow-<doc>/v<N>`; adding a new document type means adding its ID there first, then its schema file, then the re-export in `index.ts`. `versions.ts` also owns the closed enums: `PHASE_VALUES`, `RISK_TIERS` (R0..R3), `CONTROL_MODES` (`guarded | advisory`).
- `packages/persist` is the filesystem engine: `atomicWriteFile` (temp + rename, symlink refusal, Windows EPERM/EBUSY retry), `ProcessLock` (`engine.lock` created exclusively with the `wx` flag; a dead holder is stolen with one retry, a live or unreadable holder is refused, a re-entrant acquire is a `LockReentrancyError`), `AuditChain` (hash-chained `events.jsonl` + `chain.json`), `project-store.ts` (`loadProject` returns absent, invalid with a cause, or valid with the derived phase; `createProject` requires the held lock, checks for an existing record inside it, and never overwrites), and `layout.ts`, the single source of every path under `.legion-flow/`. Callers reach all of these through `Workspace.at(root)` in `workspace.ts`: a handle exposing `root`, `paths`, `audit`, `lock`, and `project` (`load`, `create`), built without I/O. The store's free functions are not exported; `project.create` additionally requires the `HeldLock` of that workspace's own engine lock. `status`, `doctor`, and `init` all read the project through the handle, so they cannot disagree about it. The handle also exposes `specs` (`load`, `current`, `create`) and `approvals` (`list`, `forSubject`, `record`); `phase.ts` is the one home of phase derivation and returns reasons (an invalidated approval, a dangling `current` pointer) that `status` renders as warnings. The config fingerprint (`configFingerprint` in `fingerprint.ts`) excludes the `current` pointer, the record's one mutable field, so moving it never invalidates an approval. A spec's fingerprint covers the canonical JSON of `spec.json` and the raw bytes of `SPEC.md`; "frozen" is derived from a matching receipt, never stored. An invalid record reports phase `uninitialized` (no valid project is in force) with a `project_config_invalid` diagnostic carrying the cause. `withLock` hands its callback a `HeldLock`, which `AuditChain.append` and `rebaseline` require; the class has a private constructor, so an unguarded write is a type error. Before appending, the chain reads from `byteOffset`: a truncated log throws `AuditChainRewindRefusedError`, exactly one committed-but-unindexed event is folded into the index, anything else throws `AuditChainInconsistentTailError`. `verify` is read-only and reports an unindexed tail rather than folding it.
- `packages/gates` owns the gate catalog and tier policy (`catalog.ts`: R0 requires `approved_spec`, `approved_plan`, `deterministic_verification`; R1 adds `acceptance_coverage` and `audit_chain_intact`; R2 adds `independent_review`; R3 adds `eval_goldens`; with `map.rules` present every tier adds `architecture_conformance`), the shell-free check runner (`checks.ts`: quote-aware argv split, no expansion, output capped at 1 MB, timeout; on Windows a `.cmd`/`.bat` target runs through `cmd.exe /d /s /c` with our own quoting, recorded as `viaCmdShim`, and a check containing `%`, `^`, or `!` is refused on that path), `evaluateShip` (writes a `ship` run: content-addressed evidence files, one verdict per gate, an evidence index; a waiver never changes a verdict's status, readiness is "satisfied or waived"), and `parseWaiver`. Run and release stores live in `persist` (`ws.runs`, `ws.releases`) because phase derivation reads them: a matching release is `shipped`; the latest complete ship run at the current fingerprints with `ready: true` and every indexed evidence file re-hashing clean is `ready_to_ship`.
- `packages/engine` runs workflows defined in code: `runWorkflow`, `resumeWorkflow(runId, interruptId)`, `continueRun`, `forkRun`, each under the held lock, each returning a discriminated result (`complete | awaiting_decision | cancelled | failed | refused`), never throwing for an expected state. A step runs every node in `next` sequentially, journals each node's `{writes, next, interrupt?}` to `steps/<seq>/writes/<node>.json` before the step's snapshot folds them through the state's reducers (`overwrite | append | upsertById | custom`, plus an `overwrite()` marker), so `continueRun` replays journaled nodes instead of re-running them. An interrupt is minted (id included) into the journal entry, then its payload is written as evidence and the interrupt file as `pending`; the run stops `awaiting_decision`. `resumeWorkflow` routes by the joined decision (`approve`/`edit` to `onApprove`, `reject` to `onReject`) or, once expired, by `onTimeout` (`cancel` ends the run; `skip` to `onSkip`, else `onReject`); it marks the interrupt `consumedAt` so it cannot resume twice. Durability: `sync` snapshots every step, `exit` only the ends, `async` is treated as `sync` at M1, and R2+ forces `sync`; seq 0 is always written. `workflowFingerprint` covers names, entry, reducer kinds, and `version` (bump `version` for a logic change); a mismatch refuses with `graph_changed`. Retry: 3 attempts, 500 ms doubling to 128 s with jitter, never for deterministic errors; `sleep`, `random`, and `now` are injectable.
- `taskWorkflow(ports)` in `engine` is what `execute` runs: `materialize` (copy the tree, fingerprint it, audit `execution_started`), `spawn` (write `prompt.md` and `brief.json` under `var/cache/runs/<runId>/`, run the adapter against the tree with a timeout and the abort signal), `propose` (diff the tree against the source; more than `maxFilesTouched` is `contract_violation`; restore every out-of-contract path in the tree first, then run the task's and the receipt's checks in that corrected tree, store each kept file's bytes as `file_content` evidence, write the `legion-flow-proposal/v1` record as evidence; R0 goes to `apply` unless the optional `architecture` port reports an introduced rule violation or throws, and R1 and above raise `fs.apply_proposal` (ADR-0009)), `apply` (refuse `source_changed` unless the checkout still fingerprints as the proposal's `treeFingerprint`, write the files from evidence re-hashing each, assert the result equals `appliedTreeFingerprint`, `recordApplied` on the run, audit), `abandon` (reject). Every node has `maxAttempts: 1`; failures are `TaskExecutionError`s whose message starts with the code. `selectNextTask` picks the first unapplied task in plan order whose dependencies are applied. Tree walking, hashing, copying, and diffing live in `persist/tree.ts` (`walkTree`, `fingerprintTree`, `copyTree`, `diffTrees`; excludes `.git`, `.legion-flow`, `node_modules`; symlinks skipped).
- **The tree has two listing modes** (`persist/tree.ts`, `TreeMode`): `git` when the workspace is the top level of a git repository without submodules (tracked plus untracked-not-ignored files, so `.env` and `dist/` never enter a sandbox), `fs` otherwise and always for a materialized copy (which sits under an ignored path where git would list nothing). The mode is explicit on every call, recorded on the proposal, and apply refuses `tree_mode_changed`. `listTree`, `fingerprintTree`, `copyTree`, `diffTrees`, `detectTreeMode`; `.git` is excluded as a file or a directory.
- **Adapters never spawn.** An `Adapter` describes an argv in guest terms through a `PathMapper` and asks the tier's `exec` (on the `Materializer`) to run it against mounts it names (tree at `/work`, run dir at `/legion/run`, adapters dist at `/legion/adapters` read-only, the fake plan file). An `ExecSpec` carries three kinds of environment: `env` (secrets and host state, travel by name under Docker with the value only in the client env), `constants` (declared, safe to record, inline as `NAME=value`), and `baseUrl: {envName, alias}` (the tier fills `http://<proxy>:8080/<alias>` when a proxy exists, nothing on the host). `stdoutPath` captures the whole stdout to a host file for parsers. `packages/adapters`: `buildAdapterEnv` (`mode: host` applies the base allowlist plus the adapter's credential by name; `mode: container` forwards nothing from the host), the `fake` adapter (`dist/fake-agent.js <prompt> <tree> <plan|->`; scripted by `.legion-flow/var/fake-adapter.json` `{edits, exitCode, sleepMs, http}`), `definitions.ts` (`CLAUDE_DEFINITION`, `CODEX_DEFINITION`: binary, vendor prefix, profile, credential and base URL variables, provider route, container constants `HOME=/home/node` and `CODEX_HOME=/home/node`, install hint; `AGENT_CLI_VERSIONS`, `agentImageTag`, `agentDockerfile`), `vendor.ts` (the two real adapters: inside a container the credential constant is `legion-flow-placeholder` and the real value is never forwarded; on the host the real value travels by name), `usage.ts` (`parseClaudeOutput` reads the single JSON result document, `parseCodexOutput` the JSON event lines; unknown is stated, never guessed), `adapterById`. `spawnFrozen` and `resolveCommand` live in `engine`: on Windows a bare command resolves through `where.exe`, prefers `.exe`, and runs a `.cmd` shim (npm installs `codex` that way) through `cmd.exe /d /s /c` with our own quoting, refusing `% ^ !`; on Windows a timeout or abort ends the whole process tree (`killProcessTree`, `taskkill /T /F`); on POSIX the child leads its own process group, which gets SIGTERM and then SIGKILL after `KILL_GRACE_MS` (slice r).
- `packages/sandbox`: `SANDBOX_TIERS` (`unhardened` and `vm-docker` available), `enforcementReport(tier, settings)`, `createMaterializer({tier, strategy, paths, runId, settings, docker})` = a tree strategy (`copy` under `var/sandbox/<runId>/tree`, or `worktree` under `var/worktrees/<runId>`: `git worktree add --detach HEAD` plus an overlay by hash of the working-tree differences, refused outside git or mid-merge) plus a tier exec (`hostExec` via `spawnFrozen`; `dockerExec` = `docker run --pull never --rm --name lf-<runId> --network none --read-only --cap-drop ALL --security-opt no-new-privileges --init --tmpfs /tmp --user <uid:gid> --pids-limit --memory --cpus`, mounts as `-v`, env as `-e NAME` only with values in the client's environment, then the image (the pinned Id once preflight resolved one, `runImage(settings)`) and the guest argv; timeout and abort `docker kill` the container by name). `DockerCli` is the one seam to the client (`realDockerCli` spawns `docker` with its own client env: PATH, HOME, DOCKER_*). `dockerPreflight` checks `docker_cli`, `docker_daemon`, `docker_linux_engine`, `docker_image` (never pulls; `FIX: docker pull <image>`; one inspect reads `{{.Id}}|<first RepoDigest>`, and since slice (x) `preflightTier` in `cli` sets `DockerSettings.imageId` to that Id on the shared tier so every container of the invocation runs by it, ADR-0015; an unreadable Id fails the check; a pinned image gone at spawn is a named `spawnError`), and `docker_probe` (a hardened container bind-mounting a scratch dir on the workspace drive and the adapters dir, writing through the mount, reporting its uid via `node`); `doctor` runs the first four through the probe and never starts a container. Settings come from `project.json` `sandbox.docker` (optional, no schema defaults so fingerprints never shift on upgrade; defaults in `resolveDockerSettings`: `node:22-alpine`, 2g, 2 cpus, 512 pids, `1000:1000` on Docker Desktop or the invoking uid on Linux). The preflight report and the enforcement report are recorded as `sandbox_tier` evidence on every run, and the exact `docker run` argv on the `adapter_outcome` evidence.
- `packages/egress`: `validateRoutes` (structural, dependency-free, duplicate aliases refused), `evaluatePolicy(routes, method, url)` (pure: `/<alias>/...` forwards, anything else 403, `CONNECT` 405, `/healthz` 200), `createProxyServer({routes, secrets, log})` (the same code in-process in tests and in the container; overwrites every configured secret header from `secrets`, drops hop-by-hop headers, streams bodies, 504 on a 120 s upstream timeout), `proxy-main.js` (the container entrypoint: reads `egress-routes.json` from its own mount at `/legion/run`, which on the host is `var/egress/<runId>`, a directory the agent never sees, so the agent cannot rewrite the log before it is hashed; secrets from its env; appends `egress.jsonl`; writes `egress-ready`; listens on 8080; exits 78 when a secret variable is unset), `summarizeEgress`. **The container-side code must stay dependency-free**: the egress dist is bind-mounted alone, so an import of `zod` or another workspace package there crashes the proxy before it reports ready. In `sandbox`, `startEgress` creates `lf-net-<runId>` (`--internal`), runs `lf-proxy-<runId>` on it (kept, not `--rm`, so its logs survive; `--add-host host.docker.internal:host-gateway` so a Linux engine resolves the host too), connects it to a second per-run network `lf-out-<runId>` (never the shared default bridge, where other containers could borrow the key), polls the ready file, and `stop()` removes both and summarizes the log; `dockerExec` does this whenever routes exist and sets `LF_EGRESS_URL` for the agent. `cleanupStale` removes labelled leftovers older than a day as the `docker_stale_cleanup` preflight check. - `packages/cli` is Commander with thin handlers. `bin.ts` inspects `argv[2]` only: sibling verbs are refused with exit 2 before Commander runs, a bare invocation defaults to `status`, and Commander usage errors are mapped to exit 2. `runner.ts` owns the CLI contract: it validates every `ResultEnvelope` against the schema, renders JSON or text, and maps status to the exit code. `commands.ts` holds the handlers; `catalog.ts` holds `COMMAND_CATALOG` (name, summary, usage, options as registration data, milestone, optional handler) plus the two sibling-verb refusal lists; `cli.ts` registers every catalog entry with Commander; `doctor.ts` runs readiness checks as an ordered list (`DOCTOR_CHECKS`) that reads the machine only through a `SystemProbe` port (`realProbe` in production, a scripted fake in tests), so every verdict is testable on any host; the Node floor is the one constant `NODE_FLOOR`, tested against `engines.node` in both manifests.

**Adding a CLI command touches one place**: a `defineEntry` in `catalog.ts`. An entry without a handler is a planned verb: it registers, accepts any argv shape, and answers a `refused` envelope with code `verb_not_implemented` naming its milestone. `options` is registration data and `usage` is the human synopsis; they are not two copies of one thing. A handler is a function from `CommandContext` (cwd, isTTY, workspace) and options to a `ResultEnvelope`; it reaches state only through `ctx.workspace`; it never writes to stdout, never sets an exit code, and never sees `--json`. Facts a human needs (project name, adapter) travel as `info` diagnostics so `--json` consumers get them too. `help-all` is exempt from the envelope and is registered directly on Commander. An entry may instead carry a `server` (today only `mcp`): `cli.ts` calls it outside the runner because it owns stdout, and it loads its dependencies by dynamic import so other verbs never pay for them.

### State layout

`.legion-flow/project/` is durable and intended to be committed. `.legion-flow/var/` is ephemeral, rebuildable, and gitignored by a `.gitignore` that `init` writes inside `.legion-flow/`. The root `.gitignore` also excludes `var/`, `sandbox/`, `worktrees/`, and `engine.lock`.

### Code conventions

- NodeNext module resolution with `verbatimModuleSyntax`: relative imports use `.js` extensions even in `.ts` source.
- Tests are `node:test` + `node:assert/strict`, under `packages/<pkg>/test/*.test.ts`. In the CLI package, `commands.test.ts` and `runner.test.ts` call handlers in-process and assert on envelopes (the envelope is the test surface); `bin.test.ts` spawns the built binary only for what `bin.ts` itself does (sibling refusal, bare-command default, `help --all` rewrite, exit mapping).
- Audit rebaseline and gate waivers require a reason of at least 24 characters.

## Invariants to preserve

These come from the design report and the sibling tools; do not relax them when implementing new verbs.

- Control modes are `guarded | advisory` only. Never add `autonomous`.
- Human-only verbs (`decide`, `ship`, future `approve`) are never executed by an agent. `decidedBy.kind` is always `"human"` and must name an entry in `project.json` `decisionOwners`.
- Gate verdicts are tri-state (`satisfied | unsatisfied | unevaluable`). Missing or hash-drifted evidence is `unevaluable`, never a pass. A `blocked` result is the product, not something to work around.
- Exit codes, implemented in `runner.ts` and `bin.ts`: 0 for `ok`/`ready`, 2 for `refused`/`usage_error`/sibling verb, 3 for `blocked`/`awaiting_decision`, 1 for unexpected errors (including a handler returning an invalid envelope). Three documented exceptions to "one envelope per command": `mcp` (stdout belongs to the stdio protocol, or HTTP writes only to stderr; without exactly one transport it exits 2 on stderr), `help-all` emits text only, and a Commander usage error prints to stderr and exits 2 with no document, because parsing failed before any command existed.
- Adapter HTTP config carries `apiKeyEnv` (an env var name), never an inline `apiKey`.
- Decisions are compare-and-set against a `pending` interrupt and carry an `idempotencyKey`; approvals are single-use.
- No runtime dependency on LangGraph, Mastra, Cognee, Browser Use, or DeepEval packages. Patterns are reimplemented, not imported.
- Docs must not claim Windows filesystem or network isolation parity with Linux/macOS, and must not use `production-ready` or `generally available`.
